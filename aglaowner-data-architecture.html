Entity relationships

Every table hangs off profiles, the one row per verified phone number that a person becomes a seller, buyer, or referrer through — there is no separate account system.

03

Write path — publishing a listing

The mechanism that matters here: the listing exists in Postgres before payment, sits invisible to the public catalog until payment confirms, and the money never touches the browser.

04

Read path — unlocking a seller's contact

The catalog itself is public. What's gated is the one field that matters: the seller's phone number, released only through a function that checks the buyer's DigiLocker verification server-side.

06

Who can touch what

Every table below has RLS turned on the moment it's created — there is no table that ships open. The four policies below cover the whole surface.

Anonymous

Read-only on listings where status = 'active', categories, and public program stats. No inserts, no contact fields.

Owner (seller)

Full CRUD on rows where owner_id = auth.uid(), across draft, active and archived states. Can't touch anyone else's listing, ever.

Verified buyer

Same read as anonymous, plus the reveal_seller_contact() RPC — gated on profiles.digilocker_verified_at, not a table grant.

Admin

Bypasses per-row ownership via a role = 'admin' check — full read/write on config tables (credit_rules, promotions, listing_type_settings, voucher_providers) and read on everything else.

The RLS rows above are the database-level policy; the app-level gate that gets a request there in the first place is src/proxy.ts. It checks app_metadata.role (never user_metadata — that's client-editable) from the caller's Supabase session on every /admin/* request, redirecting to /admin/login (magic-link sign-in, src/app/admin/login) otherwise. src/app/auth/confirm completes that link. src/lib/safe-redirect.ts constrains the post-login ?next= redirect target to same-origin relative paths only — without it, a crafted magic-link could redirect a freshly-authenticated admin off-site.

-- every table FKs to profiles.id and every role check reads from it, so a signup
-- with no matching profiles row breaks the first write and silently fails every
-- role check. This is the first thing that must exist -- everything else assumes it.
create function handle_new_user()
returns trigger as $$
begin
  insert into profiles (id, phone)
  values (new.id, new.phone)
  on conflict (id) do nothing;
  return new;
end;
$$ language plpgsql security definer;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function handle_new_user();

-- sellers edit their own listing content freely...
create policy "sellers edit own listing content"
  on listings for all
  using (owner_id = auth.uid())
  with check (
    owner_id = auth.uid()
    -- ...but never touch status or the timers themselves —
    -- see the trigger below. A blanket owner_id-only WITH CHECK here
    -- would let a seller flip status='active' without ever paying.
  );

-- status/active_until/archive_until are set only by this trigger,
-- which runs as the table owner and is the sole path from the
-- payment webhook's service-role UPDATE to a live listing
create function guard_listing_status_columns()
returns trigger as $$
begin
  if (new.status, new.active_until, new.archive_until)
      is distinct from (old.status, old.active_until, old.archive_until)
     and auth.role() <> 'service_role' then
    raise exception 'status/timers are set by payment confirmation only';
  end if;
  return new;
end;
$$ language plpgsql security definer;

create trigger lock_listing_status
  before update on listings
  for each row execute function guard_listing_status_columns();

-- the HTML prototype only checked this client-side (sellRefError) —
-- promoted to a trigger so a direct API call can't bypass it
-- (plain CHECK constraints can't subquery another table in Postgres)
create function guard_no_self_referral()
returns trigger as $$
begin
  if new.referral_code_used is not null
     and new.referral_code_used = (
       select referral_code from profiles where id = new.owner_id
     ) then
    raise exception 'referrers cannot use their own code on their own listing';
  end if;
  return new;
end;
$$ language plpgsql;

create trigger no_self_referral
  before insert or update on listings
  for each row execute function guard_no_self_referral();

-- config tables: everyone reads, only admins write
create policy "anyone can read credit rules"
  on credit_rules for select using (true);

create policy "only admins edit credit rules"
  on credit_rules for all
  using (exists (
    select 1 from profiles
    where id = auth.uid() and role = 'admin'
  ));
Why a function instead of a view, for contact reveal A view still runs under the querying user's row-level policy per-row; it can hide the whole row but can't conditionally hide one column while showing the rest of that same row. reveal_seller_contact(listing_id) is security definer, so it runs as the function owner, checks the caller's verification explicitly, and is the only path that ever selects profiles.phone for a seller.
Rate limit the reveal, not just the anonymous read DigiLocker verification answers "is this a real buyer," not "how many contacts has this buyer pulled in the last minute." Without a limit, one verified account can call reveal_seller_contact() across every active listing id and harvest every seller's phone number. Cap it inside the function itself — e.g. a per-auth.uid() counter in a small rate_limits table, checked and incremented before the row is returned (Postgres advisory locks or a rolling-window count both work; the point is the check lives in the same security definer function, not in a layer the client could skip).

09

Connecting real keys

The order that actually works, in one pass, first try — skip a step here and the symptom shows up somewhere confusing (a foreign-key error on the very first listing insert, an admin stuck in a redirect loop) rather than at the step that caused it.

  1. Run the migration. supabase db push against the new project, or paste supabase/migrations/20260910220413_init.sql into the SQL Editor and run it once. It creates all 14 tables, every RLS policy, both listing guard triggers, the rate-limited contact-reveal RPC, and the on_auth_user_created trigger — that last one specifically has to exist before anyone signs in, or their first write fails on a foreign-key violation with no obvious connection to "missing trigger."
  2. Set the three env vars in app/.env.local (never commit this file — already gitignored):
    VariableWhere to find it
    NEXT_PUBLIC_SUPABASE_URLProject Settings → API → Project URL
    NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEYProject Settings → API → the anon/publishable key
    SUPABASE_SERVICE_ROLE_KEYProject Settings → API → service_role key — server-only, never NEXT_PUBLIC_
  3. Provision the first admin by hand. The login form deliberately passes shouldCreateUser: false — it will not create an account for an arbitrary email (see the access-control section above). Create the user first (Authentication → Users → Add user, in the dashboard), then grant the role via SQL, since app_metadata is not settable from the client: 
    -- run once, in the SQL Editor, after creating the user in the dashboard
update auth.users
set raw_app_meta_data = raw_app_meta_data || '{"role": "admin"}'::jsonb
where email = 'you@aglaowner.in';
  4. Restart the dev server — Next.js only reads .env.local at boot, so a running next dev from before the keys existed will keep failing closed.
Verification checklist — run all four
  1. Visit /admin signed out → redirected to /admin/login, not a 503 (503 means step 2 above is incomplete).
  2. Sign in as the admin from step 3 → lands back on /admin, not bounced to login again (a bounce means the app_metadata update didn't take, or the session cookie wasn't picked up — re-check the UPDATE ran against the right user).
  3. Check select * from profiles where id = auth.uid() as that admin → one row exists automatically (proves the on_auth_user_created trigger fired).
  4. Run supabase db advisors (or the get_advisors MCP tool) — should report no missing-RLS or security-definer warnings on anything in this migration.
